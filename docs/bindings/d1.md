# D1

SQLite databases bound to `env.*` through workerd's own `d1-api`
implementation, with the data plane on `vrt-sql`.

**Status: Partial**

## Wrangler configuration

From `examples/standalone-d1/wrangler.jsonc`:

```jsonc
{
  "d1_databases": [
    { "binding": "DB", "database_name": "d1-demo-db", "database_id": "standalone-d1-demo" }
  ]
}
```

## Where it runs

- The tenant binding is workerd's internal `cloudflare-internal:d1-api`
  wrapped binding, so `env.DB.prepare(...)`, `.batch()`, `.exec()` and
  friends are workerd's own client code.
- `facade-d1` — a system worker that receives the `/query` and
  `/execute` posts, strips all inbound `x-vrt-*` headers, and forwards
  with host-injected identity to `vrt-provider`.
- `vrt-provider` — authorizes and forwards `/internal/bindings/v1/d1/
  {bindingId}/{query|execute}` to `vrt-sql` over the internal network
  with a signed-token auth secret.
- `vrt-sql` — single-writer SQLite engine with lease/fencing,
  `_vrt_dedup` same-transaction deduplication, and object persistence
  (`[persistence] backend = "fs"` with a CAS lease, or `none` for
  tests/dev only).

## Backends

There is exactly one D1 data plane: `vrt-sql` (rusqlite). Persistence is
configured in `vrt-sql.toml` — the fs object-store backend uploads
segments to a local or object-store root behind a CAS lease; there is no
replication beyond local fsync.

## Known differences from Cloudflare

- `database_id` and `database_name` are user-side identifiers. The real
  `databaseId` is minted at deploy time as the first 26 hex chars of
  `sha256("vrt-d1:{tenant}:{user_id}")` — the signed snapshot covers the
  derived value and a worker can never pick an arbitrary id
  (`vrt-local/src/worker_pkg.rs`). Bindings sharing the derived id share
  the database, matching Cloudflare's account-scope semantics.
- `database_id` is optional on standalone: a missing value falls back to
  the binding name. (`database_name` is optional too; both are carried
  as display metadata only.)
- Errors surface in workerd's `D1_ERROR: …` shape — HTTP 200 with
  `{success:false,error:"D1_ERROR: …"}` so the binding throws a D1
  error, never an opaque 500.
- Single writer, no read replication, no Time Travel / point-in-time
  restore, no `.dump()` endpoint verified — these Cloudflare features
  are not present. `withSession` behavior is not documented / unverified.
- Durability: local fsync plus segment upload to the configured object
  persistence; there is no cross-host replication.

## Unsupported keys and error shape

Accepted keys per `d1_databases[]` entry: `binding`, `database_name`,
`database_id`, `preview_database_id`, `remote`. Anything else fails the
deploy:

```
[VRT_CONFIG_UNSUPPORTED_FIELD] d1_databases[0].<key> is not supported by the VRT runtime (d1_databases[0].<key>)
```

Wrangler's `migrations_dir` (D1 migration directory) is a top-level key
outside the whitelist and fails with `VRT_CONFIG_UNSUPPORTED_FIELD` —
there is no D1 migration runner.

## Examples and tests

- `examples/standalone-d1` — `d1_databases` in `wrangler.jsonc`.
- `examples/standalone-cron`, `examples/standalone-queue` — D1 used for
  e2e side-effect assertions.

- `vrt-provider/tests/d1_wire.rs` — provider-side D1 wire tests.
- `vrt-sql/tests/engine_tests.rs`, `vrt-sql/tests/persist_tests.rs` —
  engine and persistence tests.
- `vrt-host/tests/d1_smoke.rs` — end-to-end smoke test (skips without a
  real workerd).
