# D1

SQLite databases bound to `env.*` through workerd's own `d1-api`
implementation, with the data plane on `vrt-sql`.

**Status: Partial**

## Wrangler configuration

From `examples/standalone-d1/wrangler.jsonc`:

```jsonc
{
  "d1_databases": [
    { "binding": "DB", "database_name": "d1-demo-db", "database_id": "standalone-d1-demo" }
  ]
}
```

## Where it runs

- The tenant binding is workerd's internal `cloudflare-internal:d1-api`
  wrapped binding, so `env.DB.prepare(...)`, `.batch()`, `.exec()`,
  `.raw()` and `.dump()` are workerd's own client code.
- `facade-d1` — a system worker that receives the `/query`, `/execute`
  and `/dump` posts, strips all inbound `x-vrt-*` headers, and forwards
  with host-injected identity to `vrt-provider`.
- `vrt-provider` — authorizes and forwards `/internal/bindings/v1/d1/
  {bindingId}/{query|execute|dump}` to `vrt-sql` over the internal network
  with a signed-token auth secret.
- `vrt-sql` — single-writer SQLite engine with lease/fencing,
  `_vrt_dedup` same-transaction deduplication, and object persistence
  (`[persistence] backend = "fs"` with a CAS lease, or `none` for
  tests/dev only).

## Backends

There is exactly one D1 write data plane: `vrt-sql` (rusqlite).
Persistence is configured in `vrt-sql.toml` — the fs/S3 object-store
backend uploads a snapshot, per-commit segments and the manifest behind a
CAS lease.

A separate, opt-in `vrt-sql follower` process tails that chain into an
immutable read-only generation without taking the lease
([d1-follower.md](../d1-follower.md)). With `vrtSql.replicas` configured, the
provider routes eligible `/query` reads to followers using the tenant's session
bookmark; `execute`, writes sent through `/query`, and `dump()` stay on the
writer. A replica that is behind the bookmark (or would write) answers with a
typed 409 and the provider retries once on the writer.

## Known differences from Cloudflare

- `database_id` and `database_name` are user-side identifiers. The real
  `databaseId` is minted at deploy time as the first 26 hex chars of
  `sha256("vrt-d1:{tenant}:{user_id}")` — the signed snapshot covers the
  derived value and a worker can never pick an arbitrary id
  (`vrt-local/src/worker_pkg.rs`). Bindings sharing the derived id share
  the database, matching Cloudflare's account-scope semantics.
- `database_id` is optional on standalone: a missing value falls back to
  the binding name. (`database_name` is optional too; both are carried
  as display metadata only.)
- Errors surface in workerd's `D1_ERROR: …` shape — HTTP 200 with
  `{success:false,error:"D1_ERROR: …"}` so the binding throws a D1
  error, never an opaque 500.
- Single writer. A read-only follower can materialize a replica from the
  object-store chain; when `vrtSql.replicas` is configured, `/query` reads are
  routed there with bookmark checks, while `first-primary` sessions, writes and
  `dump()` stay on the writer. Manual failover is `vrt-sql promote` (CAS the
  manifest epoch from a verified follower generation); there is no automatic
  failover or replica discovery.
- Time Travel is an **offline P0**: `vrt-sql time-travel` restores a database to an indexed commit
  or signed bookmark while the writer is stopped ([d1-time-travel.md](../d1-time-travel.md)).
  There is no online API/UI, and the history window is controlled by
  `persistence.timeTravelRetentionMs`.
- `dump()` works on every local database (Cloudflare's docs limit the
  alpha-era API to databases created during D1's alpha period; this
  runtime has no such generation split). The export is a SQLite-compatible
  SQL script and the provider returns it as `application/octet-stream`,
  so workerd's `d1-api` hands the tenant an `ArrayBuffer`. The statement
  order, identifier quoting and value escaping follow workerd's own D1
  export (`src/workerd/server/d1/d1.js`, the reference implementation
  behind `dump()`): `PRAGMA defer_foreign_keys=TRUE;` first, `CREATE
  TABLE IF NOT EXISTS` for quoted names, `INSERT INTO "t" ("c1",...)
  VALUES (...)`, `''` for quotes, `\n`/`\r` restored with
  `replace(...,char(10))` / `char(13)`, `X'..'` for blobs, `NULL`, and
  `9e999`/`-9e999` for infinite reals. Engine-internal `_vrt_*` tables and
  `_cf_*`/`sqlite_*` tables are skipped, as in workerd. The output is
  byte-for-byte checked against workerd's golden vectors in
  `vrt-sql/tests/dump_tests.rs`.
- `dump()` is **not** subject to the 50 MB query-result limit on
  Cloudflare, but this implementation buffers the whole export in the
  provider: exports over 64 MiB fail closed with a bounded error instead
  of being truncated or silently succeeding. That is a local transport
  bound, not a Cloudflare limit.
- Query results are capped at Cloudflare's documented maximum: 50 MB
  (50,000,000 bytes) per statement, enforced since 2026-11-04. An
  oversized result fails with the documented text
  `D1 query result exceeded the maximum response size limit of 50 MB`,
  surfaced by `d1-api` as `D1_ERROR: D1 query result exceeded the
  maximum response size limit of 50 MB`; the statement's writes roll
  back with the rest of the batch. The cap is measured on the serialized
  result payload this data plane actually returns (Cloudflare does not
  document its own counting unit). The provider still caps one upstream
  response at 64 MiB, so a multi-statement batch whose combined results
  exceed that transport bound fails closed as an unavailable backend
  rather than being truncated.
- `raw({columnNames:false})` is the default shape (rows only);
  `raw({columnNames:true})` prepends one row of column names, including
  for empty result sets. Duplicate column names stay separate columns
  (rows are arrays, not objects).
- `PRAGMA defer_foreign_keys` is accepted (read or a boolean value) so a
  dump can be executed back through `exec()`; it only defers FK
  enforcement inside the current transaction.
- `withSession()` / `getBookmark()` are workerd's own client code and
  work against the local data plane: the session token travels as
  `x-cf-d1-session-commit-token`, `vrt-sql` signs a bookmark from the
  engine's commit position on every successful `/query`|`/execute`
  (`vrt-sql/src/bookmark.rs`), and the provider returns that header, so
  the client keeps the newest token (`localeCompare`, matching the
  bookmark's fixed-width hex order).
  - Both documented constraints are accepted. Reads and writes always
    hit the single writer, so `first-primary` and `first-unconstrained`
    are equivalent here; only read-replica placement is absent.
  - The token is a consistency hint, not a credential: authority comes
    from the signed binding identity, and a bookmark can only ever ask
    for a position the single writer has already committed. A bookmark
    from another database therefore cannot widen access — at worst the
    caller gets the local latest state, which for one writer already
    satisfies "at least this bookmark".
  - `getBookmark()` returns `null` until the session's first query, then
    a non-empty token that advances with later commits
    (`conformance/cases/d1/d1-sessions`).
- Durability: local fsync plus segment upload to the configured object
  persistence. Followers on other hosts can materialize a read-only copy,
  but this is asynchronous and there is no write replication or automatic
  failover.

## Unsupported keys and error shape

Accepted keys per `d1_databases[]` entry: `binding`, `database_name`,
`database_id`, `preview_database_id`, `remote`. Anything else fails the
deploy:

```
[VRT_CONFIG_UNSUPPORTED_FIELD] d1_databases[0].<key> is not supported by the VRT runtime (d1_databases[0].<key>)
```

Wrangler's `migrations_dir` (D1 migration directory) is a top-level key
outside the whitelist and fails with `VRT_CONFIG_UNSUPPORTED_FIELD` —
there is no D1 migration runner.

## Examples and tests

- `examples/standalone-d1` — `d1_databases` in `wrangler.jsonc`.
- `examples/standalone-cron`, `examples/standalone-queue` — D1 used for
  e2e side-effect assertions.
- `facade/test/d1.test.mjs` — facade D1 contract tests (including
  `dump`'s non-200 error surface).
- `vrt-provider/tests/d1_wire.rs` — provider-side D1 wire tests.
- `vrt-sql/tests/engine_tests.rs`, `vrt-sql/tests/persist_tests.rs` —
  engine and persistence tests.
- `vrt-sql/tests/follower_tests.rs` — read-only follower bootstrap,
  incremental tail, pinned readers, GC re-bootstrap and fail-closed cases.
- `vrt-sql/tests/replica_tests.rs` and `vrt-provider/src/d1.rs` unit tests —
  replica wire surface, bookmark/servability checks, write rejection and
  provider fallback routing ([d1-follower.md](../d1-follower.md)).
- `vrt-sql/tests/time_travel_tests.rs` and `time_travel_cli.rs` — timeline
  resolution, restore by time/bookmark, continuation, dry run, writer-lock
  refusal and retention GC ([d1-time-travel.md](../d1-time-travel.md)).
- `vrt-sql/tests/dump_tests.rs` — `dump()` golden vectors, empty export,
  restore round-trip, and the 50 MB query-result rejection.
- `conformance/cases/d1/d1-dump-raw` — end-to-end `dump()` / `raw()`
  variants / oversized-result case.
- `vrt-host/tests/d1_smoke.rs` — end-to-end smoke test (skips without a
  real workerd).
