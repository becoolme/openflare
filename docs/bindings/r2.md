# R2

S3-style object storage bound to `env.*`, served by `vrt-provider`
through the `R2Transport` facade entrypoint.

**Status: Partial**

## Wrangler configuration

```toml
[[r2_buckets]]
binding = "BUCKET"
bucket_name = "my-bucket"
```

Native `vrt.toml` equivalent (`examples/standalone-r2/vrt.toml`):

```toml
[bindings]
r2 = { BUCKET = "demo-bucket" }
```

## Where it runs

- `facade-r2` — a system worker inside the tenant's workerd process,
  exposing the `R2Transport` entrypoint.
- `vrt-provider` — serves `/internal/bindings/v1/r2/{bucket}/{op}`
  (`op` ∈ `head`, `get`, `put`, `delete`, `list`,
  `createMultipartUpload`, `uploadPart`, `completeMultipartUpload`,
  `abortMultipartUpload`), authorized against the signed
  `compute.desired` snapshot.

## Backends

`[r2]` and `[s3]` are mutually exclusive (`vrt-provider/src/config.rs`);
with neither configured, R2 operations fail closed.

| Backend | Config | Notes |
| --- | --- | --- |
| Filesystem | `[r2] dir = "…"` | Layout `<dir>/<tenant>/<bucket>/<sha256(key)>`; multipart staging with TTL'd garbage collection. SSE-C fails closed (`R2_SSEC_INVALID`). |
| S3-compatible | `[s3] endpoint region bucket accessKeyEnv secretKeyEnv` | Any S3-compatible object store; `conditionalWrites` (default `true`) must match the store's support for `If-Match` / `If-None-Match`. SSE-C is supported. |

## SSE-C (customer-provided keys)

`get`, `put`, `createMultipartUpload` and `uploadPart` accept `ssecKey`,
matching workerd: the key is **32 bytes**, supplied as a 64-character
lowercase hex string (or a 32-byte `ArrayBuffer`, which workerd encodes
to the same hex form before it reaches the provider). The binding wire
always carries the hex form; the S3 backend converts it to the
base64-encoded `x-amz-server-side-encryption-customer-key` /
`-key-MD5` headers that S3 expects.

- **S3 backend only.** The full chain is covered: ranging `get`,
  `put`, `createMultipartUpload`, `uploadPart`, and
  `completeMultipartUpload`. The backend remembers the key supplied at
  create for `complete()` (the Workers API supplies no key there); that
  memory is process-local, so an unfinished SSE-C multipart upload
  cannot be completed after the provider restarts.
- **Object metadata.** Encrypted objects expose `ssecKeyMd5`, the
  lowercase hex MD5 of the key (the Workers API documents the hex form,
  unlike S3's base64 header). Only the MD5 is persisted — never the key.
- **Wrong key.** A read with a key that does not match the object
  surfaces `R2_SSEC_INVALID` (HTTP 400) rather than returning bytes.
- **`head()`.** The Workers API has no key argument on `head()`, so the
  S3 backend cannot HEAD an SSE-C object without presenting one; use
  `get()` (which also returns metadata) when the object is encrypted.
- **Filesystem and memory backends fail closed** with
  `R2_SSEC_INVALID` for every key-bearing operation. They never store
  plaintext and claim it is encrypted.

## Known differences from Cloudflare

- Conditional writes (`onlyIf`, e.g. etag / `ifNoneMatch` semantics) are
  pushed down to the backend. With `s3.conditionalWrites = false`, an
  `onlyIf` call fails `CAPABILITY_UNSUPPORTED` — it is never degraded to
  a non-atomic write.
- The multipart chain works end to end: create → uploadPart → complete
  → get, plus abort. Staged parts have a TTL (default 7 days, mirroring
  upstream R2's `AbortIncompleteMultipartUpload` window) and per-tenant
  staging byte and active-upload caps on the fs backend.
- `complete()` returns a full `R2Object`, including the `httpMetadata` /
  `customMetadata` supplied to `createMultipartUpload`; no read-back is
  needed. All backends (fs, memory, S3) materialize both as objects,
  `{}` when the upload supplied none, matching workerd's non-list
  metadata parser.
- Limits (`vrt-provider/src/limits.rs`, `config.rs`): key ≤ 1024 B,
  `list` limit ≤ 1000, delete ≤ 1000 keys per call, custom metadata ≤
  4 KiB JSON, single-part object cap `maxObjectBytes` (default 256 MiB,
  hard ceiling 256 MiB), ≤ 64 active multipart uploads per tenant on fs.
- `r2_buckets[].bucket_name` is required and used as the bucket name in
  the local store. `jurisdiction` and `storage_class` have no
  representation and are rejected (see below).
- No presigned URLs or public bucket domains.

## Unsupported keys and error shape

Only `binding` and `bucket_name` are accepted per `r2_buckets[]` entry.
Everything else — including `jurisdiction`, `storage_class`,
`preview_bucket_name` and `remote` — fails the deploy:

```
[VRT_CONFIG_UNSUPPORTED_FIELD] r2_buckets[0].<key> is not supported by the VRT runtime (r2_buckets[0].<key>)
```
